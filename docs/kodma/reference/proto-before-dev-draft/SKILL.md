# 画布共创

把事情表达清楚，让用户与 Agent 在同一份可编辑画布上推敲。按表达目标选择场景、流程、关系、界面与必要文字，不默认手机画板、iOS 风格或开发交付。

## 路由：从当前状态进入主流程

主流程：**grill 澄清 → 最小可讨论稿 → 点选与直接改稿 → 按目标核对 → 交付画布、文档或实现。**

采用 ask-matt 的“主流程、不同入口、条件分支”组织方式，不把所有任务串成研发流水线。根据用户当前状态选择最近的入口，已有共识沿用，不要求从头重走。说明将调用其他 skill 或跳过其步骤前，先读取该 skill 的完整 SKILL.md；本节摘要不替代实际规则。只加载当前路径需要的参考。

| 当前状态 | 进入路径 | 何时回到主流程 |
| --- | --- | --- |
| 想法模糊，目标或范围未定 | 读取 [grill 机制](references/grill.md)，澄清影响本轮表达的决定 | 用户确认本轮目标后，绘制最小稿 |
| 已有文档、流程材料或架构信息 | 先读材料、查事实，再用 grill 核对冲突和缺口；按下表选择表达形式 | 关键关系明确后绘制，不重复询问材料已回答的事实 |
| 已有画布，需要点选修改 | 直接进入“在同一份画布上共创”；只有改动引入新决定时回到 grill | 修改、核对并交还编辑权 |
| 已有 App 或明确的界面需求 | 进入“App 原型到开发验收”，取得场景证据；未定的体验选择交给 grill | 原型确认后按用户目标交付或开发 |

**需要看图才能决定：**先确认本轮要比较的问题，再画必要的候选方案。绘图是澄清的一部分，不要求先回答依赖画面的问题；看稿后继续 grill，不将探索稿视为定稿。

**需要运行才能决定：**静态画布不能证明状态逻辑、系统手势或真实业务效果。提出一个有明确判定条件的最小运行实验；任务已授权时执行，否则先明确是否需要开展。取得结果后回到原画布更新结论。运行实验不自动扩大为完整开发，也不强制新建会话、工单或分支。

**进入交付：**以用户目标选择出口。只要画布即可停止；明确要求文字成果才生成文档；确认实现目标并要求开发才进入实施和实际平台验收。规模变大时按需保留交接信息，不强制 spec、ticket 或 Git 流程。

## Grill：贯穿讨论与改稿

首次处理未决目标、关系或取舍前，读取 [grill 机制](references/grill.md)。它是本草稿针对画布共创适配的 grilling 机制，保留设计树、前提依赖、分轮追问、事实自查与共识确认；不能仅用一句“需求是否明确”替代。

简单且明确的修改可直接执行，用户已经表达的选择即为本轮依据，不重新询问。进入新一轮时只处理新暴露或被改变的决定。长期项目需要持续维护领域术语和决策时，按 grill 参考中的条件进入 grill-with-docs 路径。

## 确定表达目标

- 先理解用户想说明什么、给谁看，以及想通过画布理解、比较或决定什么。从现有材料中查清事实；只有缺失信息会显著改变表达时才问一个具体问题，给出有依据的推荐。
- 从用户目标判断表达形式，不要求用户先选图的类型。一个画布可以组合多种形式，但只画本次理解所需的对象和关系，尽早给出最小可讨论稿。
- 用户要求写文档时，识别其中可以直接具象表达的场景和关系；用户明确要求文字文档、特定格式或完整论证时，保留该交付物，按需用画布辅助，不擅自替换要求。
- 不要求仓库、技术栈或开发计划。只有还原系统事实或实施代码时，才读取相关项目。术语歧义会影响表达时先统一含义，不为普通画布任务强制引入建模或研发流程。

## 按内容选择表达与核对方式

| 表达目标 | 画布形式 | 核对重点 |
| --- | --- | --- |
| 文档表达与概念梳理 | 分组、层级、关系、场景与必要的文字段落 | 原材料的关键主张、条件与例外是否保留；是否能看懂概念之间的关系 |
| 业务或服务流程 | 角色、步骤、分支、时间线或泳道 | 触发、责任、输入输出和结束条件是否明确；关键异常能否走通 |
| 架构讨论 | 系统边界、组件、依赖与数据流；按需并排比较方案 | 连线的方向和含义是否明确；现状有何证据；方案与假设是否和事实区分 |
| 界面与交互 | 可编辑界面、组件状态与必要转场 | 是否符合目标平台和产品语言；关键操作、结果及返回路径是否清楚 |

图稿应直接呈现关系，不把长文切成卡片堆满画布。空间位置、分组和连线承担主要表达；文字用于命名、必要解释和精确定义。保留不能被简化掉的条件、例外与来源，长篇依据按需引用原材料。

架构或流程中的关系不能因布局方便而虚构。将已知事实、推测、拟议方案与待确认问题区别表达；没有材料支撑时交付概念方案，不声称还原了实际系统。只有内容需要时才添加图例或注释。

## 在同一份画布上共创

1. **连接目标稿。** 每次操作 FigCraft 前按 [连接指南](references/figcraft.md) 检查安装、实例与协作。复用用户正在使用的目标稿和一个桌面实例；Agent 使用无窗口 guest 加入同一 live session，核对文档、身份和写权限。不要操纵用户的选区、视口或演示状态。
2. **绘制最小可讨论稿。** 一个需求维护一份工作稿，已有稿原位迭代，新稿保存到稳定路径。先画最能表达目标的局部或主场景，再按讨论需要展开。复用已有对象与素材，保留用户手工修改。
3. **绑定反馈与对象。** 从用户 peer 的 presence.selection 读取当前点选，结合页面、节点与父级，将用户原话绑定到明确对象，再按节点 ID 修改。读取不代表消息发送时的选区；切页、空选区或对象歧义会影响修改时，先核对对象。用户直接改稿后，比较改前快照与当前值，避免覆盖同时修改的字段。
4. **检查并交接。** 按表达目标检查结构与内容，检查本轮变化的代表区域是否可读、可选、可编辑，再确认同步、保存与回读。每轮完成后交还编辑权，等待用户下一轮反馈。

**每轮写入前主动告知：**“我正在改这份稿。你可以查看和点选；请等我说『准备好了』再动手修改。”

**全部写入、同步与保存回读成功后主动告知：**“准备好了，这轮修改已保存，现在你可以直接改稿。”随后停止写入。失败时说明实际状态，恢复并核对后再发完成提示，不把部分成功当作完整保存。

文字、节点、连线、界面控件应保持独立可编辑。截图可以作参考，照片和插画可以作素材；不要用整张图片冒充可编辑图稿。若当前工具不能表达必要的关系或交互，明确限制，与用户确定替代方式，不以静态效果冒充已验证能力。

## App 原型到开发验收

此分支用于界面、交互及产品开发目标。只需图解的任务不加载设备、控件或运行验收要求。

- **按平台建稿。** 优先沿用目标项目的品牌、设计系统与平台规范。iOS 目标按设备和系统版本采用原生风格、逻辑点、安全区、状态栏、导航栏、Sheet、键盘及原生控件行为；使用项目或设备实测值，不套用单个机型常数。其他平台按其规范绘制，不能默认套用 iOS。
- **还原实际场景。** 已有 App 优先取得同版本、同设备、同状态的运行画面及项目组件素材；先核对是否为用户所指场景，已有明确确认可沿用。新产品从主流程和关键状态展开，不穷举无关画板。
- **保持整屏可编辑。** 涉及的页面按导航、内容、弹层、工具栏等语义组织；文字为文本层，控件有可独立修改的子层。不能以整屏、键盘或工具栏截图替代结构。不要给产品界面擅加辅助说明，优先让控件表达用途。
- **验证原型。** 对代表画板按需导出，与同状态参考图同尺寸对比，检查几何、文字、图标、层级和可编辑性。用户需要试走的流程以必要状态和转场表达触发、结果与返回；记录未实现或未验证的交互，不用静态图证明行为。
- **按授权实施与验收。** 用户确认实现目标并要求开发后，再按定稿修改代码，在实际目标平台的同页面、同状态验证界面、交互和业务结果。iOS 验证需覆盖相关设备适配、键盘、手势等真实行为；构建成功不等于产品验收。实现偏差修实现，设计意图变化则更新原稿并再次确认。

## 完成条件与出口

- **以画布交付：** 用户可以打开并继续编辑，目标场景、关系或方案表达完整，本轮检查结果和剩余不确定性清楚。流程用实际案例试走，架构按来源核对关系，概念或文档表达按原材料检查关键含义。用户确认前，不声称已形成共识。
- **以文档交付：** 用户需要文字成果时，根据已确认内容生成所需文档，保留必要条件、依据与画布引用，不默认额外生成一份重复长文。
- **以实现交付：** 只有任务包含开发时进入实施；按目标平台运行验收，明确已验证与未验证范围。

图稿本身可以是完整成果，不必继续开发。交付时提供可打开的工作稿，简要说明本轮解决了什么以及仍需确认的唯一下一项；没有待办时直接结束。
