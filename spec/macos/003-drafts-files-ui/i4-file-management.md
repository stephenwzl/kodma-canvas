# S003 I4：稿件列表与文件管理

日期：2026-11-17。实现及本轮工程验证完成，实际截图待用户验收；I5 与 S003 整体亲验未结项。

## 行为与实现

首页合并全部受管索引及外部最近记录，按最近操作排序，剩余受管稿按保存顺序接续。20 条限制只属于参考宿主的最近记录，不再限制受管稿件；搜索仅过滤名称，忽略英文大小写及首尾空白，清空恢复列表。长名称截断，完整名称与路径通过悬停提示辨认；相同名称仍按路径 / 稳定标识区分。列表菜单、确认和排队动作均捕获路径；鼠标或菜单追踪中的旧行不会被重绑给另一份稿件。

外部文件只有“从列表移除”，沿用原命令清除记录，不关闭已打开文档，不写入或删除源文件；显式重新打开可再次登记。原生列表打开改用 file.open，缺失文件报错后仍保留明确的移除入口，参考宿主 file.openRecent 的原行为不变。

受管菜单提供“移到废纸篓…”和“移除失效记录…”。确认调用 draft.trash：保存目标修改，预先原子提交不含目标的索引，调用宿主的系统废纸篓服务，系统成功后才移除内存记录并关闭目标及其分支标签。失败保留原文件 / 标签 / 列表并恢复索引；恢复写入也失败时保留错误，下一次启动可从仍存在的孤立文件恢复。索引预写失败不会触碰内容。目标标签删除后，旧快照按 UID 失效，不能重建文件；协作中的目标拒绝移动。

平台服务使用已有 objc2-foundation 的 NSFileManager.trashItemAtURL_resultingItemURL_error，仅启用 NSFileManager / NSURL / NSError feature，没有新增依赖或 unsafe，没有永久删除兜底。CLI、Web 和未配置服务的参考宿主不能执行系统废纸篓操作。底层写入和目标访问仍走自动化目录约束。

失效记录只在系统明确报告目录项不存在、且没有同路径打开稿件时允许移除；权限错误不被当成缺失文件。损坏的受管文件仍保留已知身份及名称，打开报真实错误，不让一份损坏文件阻塞全部其他稿件或伪造空稿。

| C09：失效 | 真实缺失、损坏和无读取权限文件均返回原错误；没有假空白标签。额外缺失受管记录明确移除，内容仍保留在隔离的移动目标中。自动回归覆盖损坏的受管文件不阻塞其他稿件 |
